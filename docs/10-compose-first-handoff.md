# Compose-first E2E target for downstream agents

The downstream E2E-bootstrap agent is **not** a human developer. It must not assume that IDE launch configurations, local runtimes or manual service startup are required.

Preferred delivery: **one Docker Compose project** that builds and runs the real application frontends/backends/workers, detected databases and message brokers, and stubs for everything **outside** the application boundary. This is a preferred design, not an assumption that a working Compose setup already exists. Investigate any evidence-based exception.

Discovery prepares .agent-context/environment-blueprint.md and the operational AGENTS.md guidance. The downstream E2E agent creates and validates Compose, Dockerfiles, dedicated environment profiles, fixtures, stubs and tests.

## Expected services

| Group | Target | Discovery responsibility |
| --- | --- | --- |
| Application | Build and run real backends, frontends, workers and consumers in containers | Identify build context, commands, ports, profiles, dependencies |
| DB | Local container(s) matching supported engine/version and schema | Identify driver/version, migrations, schema, seed/reset |
| Broker | Local container(s) and declared messaging topology | Identify queues/topics, exchanges, clients, retry/DLQ |
| External integrations | Deterministic stubs at each out-of-boundary API or protocol | Identify clients, URL override, contracts, auth, failure cases |
| Authentication | Test identities, roles and safe simulated boundary where external | Locate auth flows, roles, keys and callback config |
| E2E runners | Playwright UI, Newman API-only, async checks and evidence | Locate entry points, assertions, fixture needs, reports |

## Runtime design principles

- Compose **profiles** select optional services, such as debug and E2E runners. Core apps, DBs and brokers should generally be started without an optional profile. This is different from **application profiles** (for example Spring e2e or other config overrides).
- Use Compose **build** to create images from the checked-out applications rather than depending on a developer's previously built artifacts or IDE.
- Run all in-scope app components as their real implementation. Never stub an internal service just because it is inconvenient to start.
- Use service DNS names on the Compose network for container-to-container references, not localhost.
- Add healthchecks and dependency readiness. Bare depends_on establishes start order but does not itself wait for a healthy dependency.
- Allow the E2E agent to introduce **separate configuration files / application profiles** as needed; do not overwrite developers' existing local/prod configurations. Prefer explicit environment mappings for service endpoints and flags.
- Distinguish container env_file and environment (with environment taking precedence) from docker compose --env-file (Compose interpolation); record file paths, precedence and defaults.
- Commit only sanitized example env files; .env.e2e.local or credentials must be ignored. Do not commit tokens, customer data or raw transcripts.
- Provide reproducible seed/reset (DB, queues and stubs), health, logs, observed effects and teardown.
- Prevent accidental outgoing requests to production/shared external systems. Validate boundaries and external network behavior during downstream bootstrap.

## Handoff detail required

For each service capture: **name, ownership, source path, build context or version evidence, command, container port, service DNS, prerequisites, health, profile/config selection, environment names, fixtures, sources, confidence and downstream actions**.

For each external integration capture call site, protocol, URL override, contract, auth type, success/error response and timeout/retry behavior. For each E2E interface capture test entry, roles, data, assertions, reset and artifact location.

Clearly label each runtime statement as declared, inferred, or observed; source-derived commands are not proof they work.

## Future bootstrap acceptance (not discovery completion)

The future agent must demonstrate a reproducible compose config, clean builds, healthy required services, controlled external boundaries, repeatable seed/reset, UI/API/async checks and traceable evidence tied to the code revision.
